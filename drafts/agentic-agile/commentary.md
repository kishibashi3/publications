# 解説：原則と指針は何から出ているか

2026-09-19 · Kazuhiro

## 0. この文書について

本書は解説であって、規範ではない。ここに書かれたものに従う実行者はいない。述べるのは、原則と指針が「なぜそう書かれたか」だけである。

したがって本書は版を持たない。準拠先も持たない。改訂の手続きにも入らない。規範側が改訂されれば、本書は追随して書き直される。逆に本書を書き直しても、規範は変わらない。

原則の側に説明を書かない方針をとっている。規範文書が持つのは「何に従うか」であり、「なぜそれに従うか」を同じ文書に置くと、理由への同意が遵守の条件になってしまう。理由は、従う根拠ではなく、改訂を議論するときの材料として、別の場所に置く。改訂の根拠そのものは書き直し案 §1 が定める観測——「本書に準拠する案件規則の改訂記録のうち、本書が妨げになった、または不足していた事例」（この「本書」は書き直し案自身を指す）——であって、解説ではない。

本書は書き直し案（原則 3 ＋指針 6）を対象とする。承認前である。承認され版が付いた後は、この宣言を「対象: Agentic Agile Principles v2（版 N）」の形に置き換える。本書は版を持たないので、どの版を説明しているかは、ここに書く一行でしか示せない。

先行する v1（A1–A5・B1）との対応は次のとおり。

| 書き直し案 | v1 |
| --- | --- |
| P1 権威は書かれたものに宿る | A2 明示性（前半） |
| P2 開発は憲法の連鎖である | （対応なし） |
| P3 憲法は改訂される | （準拠先に委ねていた部分） |
| D1 判断の配分 | A1 |
| D2 意味の一意性 | A2（後半） |
| D3 生成と判定の分離 | A4 |
| D4 段階的委任 | A5 |
| D5 確率的品質 | A3 |
| D6 境界 | B1 |

v1 は 6 つを横並びに置いていた。書き直し案は、そのうち何が原則で何が原則から出るものかを分けている。新しく足された原則は P2 だけである。

ただし、対応表に現れない変更がある。まず目的である。v1 の目的は G1「価値を早く継続的に届ける」だったが、書き直し案の目的は「人間の判断を、最も価値のある判断に使い切る」に入れ替わっている。原則の並べ替えより大きい変更で、指針 D1 の内容が目的の位置に上がった形になっている。

次に、言明の一部が前提に移った箇所が二つある。v1 A4 の前半——同じモデルが同じ誤りを共有しうること——は、指針ではなく §2 の前提に移った。A4 の残り、すなわち生成と判定を分ける部分だけが D3 になっている。A1 も同じ形で、前半——実行は安価であり、人間の判断が希少資源となる——が §2 の前提に移り、D1 が引き継いだのは残りの「希少な判断を、最も価値のある判断に配分する。不要な判断をなくすことも成果である」だけである。

さらに、内容そのものが動いた箇所がある。D3 の「自らの成果を自ら承認しない」には v1 A4 に対応する文がなく、追加されたものである。B1 の「エージェントが参照・送信できる情報」は D6 で「実行者が参照・送信できる情報」になり、人間を含む範囲に広がった。観測の記述も、v1 の「本書の原則が妨げになった、または不足していた事例」から書き直し案の「本書が妨げになった、または不足していた事例」に変わり、原則だけでなく指針と前提も見直しの根拠に入っている。

対応表が示すのは ID の対応であり、ここに挙げた移動・追加・拡張は表からは読めない。

## 1. 前提

書かれている前提は三つしかない。実行が安く、速く、いくらでも繰り返せること。希少なのは人間の判断であること。出力が確率的にばらつき、同じ生成元は同じ誤りを共有すること。

この三つだけを書いたのは、前提が変わって答えが変わる部分がここだからである。人が有限であることも、要求が変わることも、前提としては正しいが、以前と変わっていない。変わっていない前提から出る結論は、以前と同じ結論になる。書く必要がない。

三つは独立ではない。実行が安いから何度でも試せて、何度でも試せるから人間が全部は見られず、見られないから判断の置き場所が問題になる。そして出力がばらつくので、一回見て良かったことは次回も良いことを保証しない。点で確かめる方法が効かなくなるのは、この三つが同時に成り立つときである。

## 2. 原則ごとの成立理由

### P1 権威は書かれたものに宿る

この原則は「書かれたルールと書かれた価値だけに従う」で止めることもできた。止めずに「書かれていないものは、存在しないものとして扱う」まで踏み込んでいる。踏み込む必要がある理由は二つある。

一つ目は、実行者が背景を共有しないことである。人間の実行者は、書かれていない前提を持っている。常識、慣行、前の案件の記憶、その場の空気。それが機能したのは、実行者が同じ環境に長くいて、外れたときに周囲が止めたからである。エージェントにはそれがない。文脈は毎回組み立て直される。そして書かれていないものを参照しようとしたとき、エージェントは「参照できなかった」とは言わず、もっともらしく埋める。しかも埋め方は確率的なので、同じ欠落が毎回同じようには埋まらない。「書かれていないが弱い権威はある」という状態を許すと、この確率的な穴埋めに権威を与えることになる。

二つ目は、P3 のためである。改訂できるのは、対象があるものだけである。暗黙の運用が権威を持ちうるなら、規範を改訂しても実行は変わらないことがあり、変わらなかった理由を記録することもできない。改訂可能性は明示性の上にしか立たない。P1 を弱めると、P3 が空文になる。

代償はある。書かれていない良い慣行は、いったん効力を失う。それは失われたままにはならず、妨げになった事例として観測に現れ、書かれた時点で戻ってくる。P1 は良い慣行を否定しているのではなく、良い慣行が通る経路を一本にしている。

### P2 開発は憲法の連鎖である

この原則の要点は、各層が二つのことを同時にやる点にある。自らの憲法に従って執行し、かつ下位の憲法を書く。

従来の階層は、役割で分かれていた。上の層が方針を決め、下の層が実行する。層ごとに仕事の種類が違った。ここではそうなっていない。すべての層が同じ形をしていて、違うのは扱う粒度だけである。だから層を一つ増やしても減らしても、構造は変わらない。

執行と立法を分けないのには理由がある。執行だけの層は、規範を良くできない。現実に触れて不具合を見つけても、それを反映する先を持たないからである。下位を書くだけの層は、書く根拠を持てない。自分では執行していないので、観測がない。同じ主体が両方をやるとき、執行で得た観測がそのまま下位の憲法の改訂根拠になる。この経路を作るために、二重性が要る。

そのうえで、準拠先 §2 は「改訂を提起した者は、その改訂を承認しない」と定めている（承認するのは、準拠先 §1 により、その規範文書の所有者である）。これは準拠先に既に書かれていることの紹介であって、本書がそれを定めているのではない。執行しながら下位を書くことは許し、自分が提起した改訂を自分で承認することは許さない。この非対称が、二重性を利益相反にしないための仕掛けになっている。

「実行者が人間かエージェントかを問わない」というのは、層を誰がいるかで定義していない、という意味である。層は、何に従い何を書くかという関係で決まる。人間が担当している層とエージェントが担当している層の間に、構造上の違いはない。実行主体が入れ替わっても層の定義は変わらないので、委任の進み方に合わせて規範を書き直す必要がない。ここが §4 で述べる既存の枠組みとの分岐点になる。

### P3 憲法は改訂される

憲法が固定なら、前提が変わったとき、実行者は「従って失敗する」か「黙って外す」かのどちらかを選ぶ。どちらも記録に残らない。改訂を手続きにすると、前提が変わったという事実そのものが記録として蓄積する。改訂は妥協ではなく、観測を残すための唯一の形式である。

手続きの中身を準拠先に委ねているのは、改訂の仕方が原則の内容から独立だからである。原則が変わっても、改訂の手続きは変わらない。独立なものを同じ文書に書くと、片方の改訂が他方を巻き込む。

## 3. 指針がどの原則から出るか

- **D1 判断の配分（P1・前提）** — 判断が希少であることは前提から出る。だがそれだけなら「節約せよ」という心構えで終わる。配分が操作できるものになるのは P1 からである。判断点がどこにあるかは書かれたものにしか存在しないのだから、判断点を減らすとは、文書から消すことに他ならない。P1 がなければ「誰かが暗黙に見ている」が成立してしまい、配分は測ることも変えることもできない。
- **D2 意味の一意性（P1）** — 書かれたものだけが権威なら、書かれたものの読みが一つに定まらない限り、権威も定まらない。多義語は「書かれているのに何に従うか決まらない」という状態を作り、これは P1 の破れである。変更を版として行うのも同じ理由による。意味が黙って変われば、文書を変えずに従うべき内容が変わることになる。
- **D3 生成と判定の分離（P1・P2・前提）** — 前提から出るのは半分だけである。同じ生成元が同じ誤りを共有するなら、自分の出力を自分で点検しても共有された誤りは残る。ここまでなら、別のモデルを使えばよいという技術的な対策で済む。P2 が加わって初めて、これは構造の話になる。執行と承認が同じ層で閉じれば、改訂が観測に基づかなくなるからである。そして P1 がなければ、判定の基準が書かれていないまま分離することになり、分離した判定者が同じ暗黙の前提に戻る。三つ揃って初めて分離が意味を持つ。
- **D4 段階的委任（P2・前提）** — 出力が分布であるなら、信頼は測るしかない。測ったうえで自律をどこまで与えるかは、能力の評価ではなく層の境界をどこに置くかという問題で、これは P2 から出る。責任が人間に留まるのも、層の所有者が人間だからである。P2 を外すと、D4 は「うまくいったら任せる」という場当たりになる。
- **D5 確率的品質（前提）** — 六つのうち、原則を経由しない唯一の指針である。前提から直接出るので、前提が覆れば最初に落ちる。逆に言えば、原則が全部書き換わっても D5 は残る。
- **D6 境界（P2）** — 層ごとに憲法が違うなら、層ごとに渡されるべきものも違う。境界は秘密保持のためというより、層の定義の裏側である。ここで閉じるのは上位の憲法ではない。準拠先 §3 が「規範文書は、準拠先を版を明示して参照する」と定めている以上、自分が従う憲法とその上位は見えていなければならない。閉じるのは、上位層が扱う案件データと判断材料のほうである。それが渡ると、実行者は自分の憲法に書かれていないものを根拠に動き始める。これは P1 の破れであり、破れを起こす材料を渡さないのが D6 である。連鎖が連鎖であるために、渡す範囲が層に応じて閉じている必要がある。

指針どうしが競合する箇所が一つある。D1 は人間の判断を減らす方向に働く。D4 は逆方向で、委任の度合いを一致率で測ることを求めるので、人間の判断を増やす。D3 も判定点を生成と独立に立てることを求めるが、判定を別の系列のモデルに置けば人間の判断は消費しないので、判定者が人間である場合に限り同じ資源を取る。両立不能ではないが、D1 と D4 は同じ希少資源——前提が希少と呼んだもの、すなわち人間の判断——の配分を取り合う。しかも最初の循環で検証すると決めたのは D4 であり、その観測は「判定の種類ごとの人間とエージェントの一致率」である。一致率を取るには人間が判定しなければならない。競合は、いつか起きるかもしれないものではなく、最初の循環のただ中で表面化する。

どちらを優先するかは、現時点で決まっていない。書き直し案 §6 は「価値の優先順位」を、必要になった時点で記録を根拠に追加するものの一覧に置いている。本書は解説であって規範ではないので、ここで優先順位を決めることはできない。決まっていないという事実だけを記す。

## 4. 既存の枠組みとの違い

エージェントを前提にした枠組みは、大きく二つの形をとってきた。一つは、工程はそのままにして各工程にエージェントを差し込む形である。PR、スプリント、レビューという単位が変わらないので、量だけが増える。もう一つは、人の役割をエージェントに割り当てる形である。これを原則として明示的に書いた例があり、Agentic-Agile の原則 4 は「人が設計し、エージェントが実行し、両者がレビューする」と述べる。従来の分業の写しである。後者の自己申告は率直で、AI-Empowered SAFe は自ら「AI が組織に組み込まれても、これらの中核テネットは置き換えられるのではなく、増幅される」と書いている。

ここで書いているものは、どちらでもない。層を役割で定義していないので（P2）、役割の割り当てにならない。単位を工程ではなく憲法に置いているので、工程に何かを差し込む形にもならない。

前提から組み直した例が存在しないわけではない。ただし、組み直されているのは一軸ずつである。承認の位置を組み直した例（GAIE は可逆性などの軸で監督の強度を決める。IETF の transaction challenge は承認を事前の一括付与から実行時・操作単位へ移す）、人が見る単位を作り直した例（Agentic SE の Merge-Readiness Pack、依存グラフから作業をエージェントが自己選択する Beads、人間向けの操作前提を捨てて出力を機械可読側に寄せた agentjj。最後の一つは、人が見ることを前提に置くのをやめた点で単位の作り直しに当たる）、品質の測り方を移した例（Lahiri の仕様妥当性メトリクス）、工程に強制力を持たせた例（Prifti らの実行可能プロセス記述）、人間レビュー義務そのものに手をつけた例（三者の立ち位置は異なる。Monperrus は提案である——人間の検査を撤去したあとに何も置かないのではなく、独立したエージェントによる審査、複数エージェントの合議、較正された不確実性の申告、自動の merge gate を置き、人間の承認を高リスクの変更・新規のアーキテクチャ選択・法的責任が要る経路に限定する、と書いている。General Intelligence Company は同じ方向の予測で、「2026 年末までに、人間がレビューするのはプロダクトと大きめのインフラの変更だけになる」と述べている。運用実績として報告しているのはトークン予算と出荷 PR 数であって、人間レビューの撤去ではない。Replit は運用報告だが、人間レビューを残したうえでエージェントを co-reviewer として足した形であり、「どの例でも、人間は自動化で外されたのではない。昇格したのだ」と書いている）。いずれも、残りの軸は従来のまま置かれている。

この最後の軸に手が伸びるのには観測の裏づけがある。GitLab の 2026 年の調査では、回答者——開発者と技術購買層 1,528 名——の 85% が「AI はボトルネックをコードを書くことからレビューと検証へ移した」に同意している。

違いは「どの軸を組み直したか」ではない。組み直しの根拠をどう決め、その決め方自体をどう改訂するかを、問いとして立てているかどうかである。

## 5. 空白

この節で空白と呼ぶのは、規範そのものをどう改訂するかが、枠組みのなかで問いとして立っているかどうかである。改訂の手続きを自らの設計に含めることは、その問いに出した答えの一つの形であって、答えの形が違っても——たとえば手続きを外に置くと明記していても——問いが立っていれば空白ではない。先に、ここで書いている体系の側がその点をどう置いているかを確認しておく。

準拠先である「自己改訂規範アーキテクチャ v1」は、§4「根」で自らを体系の根と位置づけ、「本書の版は所有者の承認そのものによって成立し、その手続きは本書の外にある」と書いている（この「本書」は準拠先自身を指す）。あわせて「第1章から第3章は、本書の内側の規範文書に適用する」とも書いている。つまり、この上位書は、自分が版と改訂の機構の内側にいるのか外側にいるのかを、自分で決めている。以上は準拠先に既に書かれていることの紹介であって、本書がそれを定めているのではない。決まっているのは位置づけと、v1 が所有者の承認済みであるという事実までで、その承認をどこに記録するかは決まっていない。

そのうえで見ると、上に挙げたどの例も、規範そのものをどう改訂するかを問いにしていない。改訂の手続きが設計に含まれていないだけでなく、外に置くという明記もない。監督の強度を規制インパクトや可逆性で決める枠組みは、その決定の仕組み自体を誰がどう改訂するかを書いていない。実行可能なプロセス記述を提案したものは、そのプロセスを誰が変えられるかに触れていない。仕様を正本に据えた枠組みでも、その constitution の改訂は「プロジェクトのメンテナによるレビューと承認」のままである。エージェント前提でエコシステムを設計した側でも、その設計を定めた規範の改訂だけは、人間の合議に戻している。

実証の側でも同じことが起きている。83 リポジトリ・7,310 件のルールと 1,540 件の改訂イベントを扱った研究は、何がなぜ変わったかを分類しているが、誰が提起し誰が承認するかを扱っていない。承認に当たる語は本文に現れない。統治と所有者に当たる語は現れるが、前者はルールが AI IDE の挙動を統べるという意味で使われており、後者は GitHub API の URL に置かれたプレースホルダである。どちらも規範自身の統治を指していない。空白は「まだ書かれていない」よりも、「問いとして立っていない」に近い。

ただし、これを「誰も気づいていない」と言うことはできない。空白の指摘は既にある。ICSE 2026 併設（ICSE-Companion 2026）の Hoda は、これまでの構想がコーディングという一つの活動の周辺に集中していると述べたうえで、AI のチームメイトを開発の全工程にどう組み込むかについての指針は現在存在しない、と明言している。したがって主張しうるのは「気づいた」ではない。かといって「埋めた」でもない。ここで書いている体系も、先に見たとおり根の承認手続きは外に置いている。循環を体系の内側に入れたのは、根より下の規範文書についてだけである。

他との差は、改訂手続きを体系に含めたかどうかではなく、**問いとして立てたかどうか**にある。他は、規範を誰がどう改訂するかをそもそも論点にしていない。こちらはそれを論点にしたうえで、内側については循環を体系に入れ、根については外に置くと明記した。明示的に外に置くことと、問いとして立っていないことは違う。この差は小さくない。

反論も二つ併記しておく。

一つ目は標本の偏りである。上記の実証研究の対象は、1 人が 49.4%、2 人が 31.3%、3 人が 12.0% と、マイクロチームに偏っている。承認の手続きを必要としない規模なのだから、改訂手続きが観測されないのは当然だ、という読みは成り立つ。大規模な組織で同じ空白があるかは確認できていない。

二つ目は、空白が機会とは限らないことである。人間向けの操作前提を捨てて出力を機械可読側に寄せた agentjj は、2026 年 2 月 15 日の commit を最後に更新が止まり、現在は archived（read-only）になっている。前提から組み直す試みが続かなかった例は既にあり、「空白なのは誰も思いつかなかったからではなく、やってみて続かなかったからだ」という読みを、現時点では排除できていない。

どちらの反論も、議論では解けない。解けるのは運用の記録だけである。
