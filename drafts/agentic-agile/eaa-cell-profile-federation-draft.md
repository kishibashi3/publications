## 1. 一つのCellから始める

Cellは、一定の目的に対する責任・権限・実行能力を備え、外部との合意に基づいて自律的に成果を実現する単位である。

最初は一つのCellで全部を扱ってよい。必要になった責務だけを子Cellへ切り出す。子Cellも同じ方法で分割できる。

EnterpriseとDomainは、全体と部分という位置の呼び名である。Platformなどの名前は担当する責務を表す。Cellの基本構造は共通である。

AAは、一つのAgenticなCellの内部で自律実行と学習を成立させる。構成上は、1 CellのEAAと位置づけられる。
EAAは、Cellの分割方針とCell間の相互作用を扱う。

複数Cellになっても内部方式は揃えない。Full Agentic、Half Agentic、人間中心の実行系を含め、合意した境界を満たす方式を各Cellが選ぶ。1 Cellであることだけで、非Agenticな実行系までAAになるわけではない。

## 2. 責務を定義してから配置する

Profileは、Cellが引き受ける責務を定義する、版付きの仕様である。
Missionは、その責務のもとで今回実現する変化・成果である。

| 概念 | 意味 |
| --- | --- |
| Profile | 何を成立させ、何に責任を持つか |
| Cell | 責務を引き受ける自律主体 |
| Mission | 今回実現する変化・成果 |
| Federation Protocol | 自律主体間の提案・合意・協働・改訂の手順 |

まず必要なProfileを列挙し、責任境界を明らかにする。その後で、同じCellで担うか、独立したCellへ分けるかを決める。

### Standard ProfileとDomain Profile

| 分類 | 内容 | 例 |
| --- | --- | --- |
| Standard Profile | 案件をまたいで再利用する責務 | Platform、Migration、Assurance、Cutover |
| Domain Profile | 企業の業務領域に固有の責務 | 契約、請求、受注 |

両者は同じ形式で扱う。EAAは共通形式とStandard Profileを提供し、Domain Profileは各Enterpriseの現実に合わせて定義する。
例示した名称は責務定義の候補であり、旧Profileの内容をそのまま新定義へ移せることを意味しない。

Profileには、目的、責任範囲、意味、必要な権限と制約、提供能力、外部とのContract、成立を示すEvidenceを記述する。
逐次指示なしに実行できる形へ明示するが、特定のAgent基盤や人員配置を要求しない。

Profileの定義と、引受Cell・Ope・予算・資源などの実際の割当は分ける。
Profileのロードとは、単に文書を読むことではなく、その適用範囲で責務を引き受け、必要な権限と能力を確保することである。文書に権限を書いただけで、権限が付与されるわけではない。

## 3. 分離は判断責任を渡すこと

一つのCellが複数Profileを引き受けてよい。
判断負荷や専門性に応じて、Profileの責務を別のOpeへ渡し、子Cellとして独立させる。

独立とは、別のOpeが合意した範囲で判断責任を引き受けることである。
作業を渡しても、判断をすべて元のOpeへ戻すなら、自律したCellへの分離にはならない。

分離時には、責務の仕様に加え、実際の権限・資源・管理対象・記録・進行中Mission・残件を引き継ぐ。
責任の空白や、同一対象への決定権の重複を残さない。

再統合も責務の引継ぎとして扱う。Profileを解除しても、未完了の仕事や外部への保証が消えるわけではない。
詳細な分離・再統合の手続きは未決事項とする。

## 4. Ope・Enabler・Executor

| 役割 | 中核となる責務 |
| --- | --- |
| Operator | Cellの成立条件、責任境界、権限、規範、例外判断を持つ |
| Enabler | 顧客や関係者と文脈を共有し、目的・優先順位・受入条件を具体化して変化を進める |
| Executor | 合意された目的・制約のもとで実行し、Evidenceを返す |

EnablerとOpeに固定的な上下関係を置かない。EnablerはMissionに応じて複数Cellを横断でき、Cellごとの1:1配置を要求しない。
顧客などに最終判断権がある場合、Enablerはその判断を成立させ、記録へ戻す。顧客接点を担うことだけで最終決定権を得るわけではない。

Opeは、実行と検証をできる限り自律系へ委ねられるようにする。
OpeのAgenticなリテラシーはCellの実行方式を大きく左右する。Enablerの中核能力は顧客理解と文脈の往復であり、同じAgent運用能力を必須としない。
技術・契約上の条件も実行方式を制約する。

## 5. 分離されたCellの自治

> 各Cellは、合意した規範・Contractの範囲内で自律する。
> 他Cellは、親Cellを含め、その判断を一方的に上書きしない。
> 変更は提案し、対象Cellの受入によって成立する。

Enterprise Cellもこの原則に従う。
全体の目的・資源・共通規範を扱う責務は、他Cellの内部を直接変更する権限を意味しない。

受入側は、合意済みの義務を果たす責任を持つ。
新しい提案を受け入れないことと、既存の義務を一方的に破棄することは異なる。
履行不能や合意不成立の扱いは明示的に協議し、親からの強制適用で解消しない。

## 6. 共通層とFederation

Cell間では、意味・規範・境界合意を参照して協働する。

| 共通層 | 役割 |
| --- | --- |
| Ontology | 各Cellの意味の違いを保持し、文脈から解釈できるようにする |
| Constitution | 採用した目的・価値・制約・権限・禁止事項を定める |
| Contract | 相互の責任、提供条件、入出力、必要なEvidenceを合意する |
| Evidenceと来歴 | 実行・判定・決定の根拠と因果を追跡可能にする |

Profileの適用やMissionは、依存する規範・Contract・意味の版を特定できるようにする。
上位の版が変わっても、下位の採用版は自動で変わらない。影響する変更は、対象Cellとの合意を通じて移行する。
採用中の規範を実行者自身が緩めてよいことにはならず、AAの自己権限の固定は維持する。

### 提案と受入

Cell間の提案は特別な行為ではなく、共通の協働手段である。

| 方向 | 提案例 |
| --- | --- |
| Enterprise → Domain | 目的・責任境界・共通規範の変更 |
| Domain → Enterprise | Ontology訂正、全体方針や制約の見直し |
| Platform → Domain | CI/CDの導入・更新 |
| Domain → Platform | 基盤機能・提供条件の改善 |

提案側が変更内容・理由・根拠を示し、受入側が影響を検証して、受入・修正要求・不受入を判断する。
判断と適用結果は追跡可能に残す。GitHubのPRはこの手順の実装例であり、必須製品ではない。

受入は毎回の人間承認を意味しない。受入側の規範と権限に従ってAgentが判断できる。人間判断が必要な場合は、そのCellの正当な判断主体へ戻す。

提案の受入・PR mergeと、Missionの成果成立は区別する。実際のOutcomeとAcceptance Evidenceを確認して完了とする。

### 横断責務

PlatformやAssuranceのような横断責務もProfileとして定義できる。
他Cellへ規則・検証・仕組みを導入する仕事は、提案と受入の共通手順で進める。

Platform CellはDomain CellへCI/CD変更をPRし、Domain Cellが受入を判断する。
横断責務を持つことを理由に、他Cellへの強制変更権限を得ることはない。
導入を目的とするMissionは、提案を提出しただけでは完了しない。

## 7. 一つのCellから分離する例

次はIaC化を題材にした構成例であり、実案件の効果を立証するものではない。

1. 一つのCellで、業務DomainとPlatformのProfileを引き受ける。
2. Enablerが顧客との会話・問題・残件をIssueへ戻し、OpeとAgentが土台・計画・実装・検証を進める。
3. 基盤の継続的な判断負荷が増えたら、別OpeがPlatform責務を引き受ける。
4. Profileに対応する権限・資源・資産・残件を移し、Platform Cellを独立させる。
5. 以後、Platformから各CellへのCI/CD変更も、各CellからPlatformへの改善提案も、提案と受入で進める。

分離前後で、何を成立させる責務かは維持できる。実行主体と接続方法が変わる。
分離の効果は、元のOpeへの判断集中が減り、成果と保証を維持できたかで確認する。

## 8. 既存文書からの変更

| 既存の整理 | 本草案での整理 |
| --- | --- |
| EAAは複数Domainの境界を統治する | 1 Cellから始め、責務を再帰的に分割・接続する |
| Profileは条件付きの追加規範 | Profileは引受可能な責務仕様。横断的な統制の成立も責務に含める |
| Platformの配置はCapability Ownership Pattern | Platform責務はStandard Profile候補。独立Cellにするかは配置判断 |
| Enterprise／Domainを中心にロールを配置 | 共通構造のCellにProfileを割り当て、独立した判断責任にOpeを配置 |
| EnablerがGoal・Priority・Outcomeを所有 | 顧客との文脈共有と変化の具体化を中核とし、最終決定権の所在を区別する |
| 上位規範への準拠 | 合意して採用した版への準拠。変更の受入は各Cellが判断する |

Ontologyによる意味差の保持、Authorityの自己拡大禁止、Evidenceによる完了判定、来歴の記録、内部方式の自治は継承する。
旧Profilesの要求集合・権限の積集合という式だけでは、新しい責務の割当や分離は表現できない。旧カタログは責務・制約・配置を整理して書き直す。

## 9. 次に具体化すること

- **合意不成立**：必要な変更に合意できない場合の調整・停止・責務返還・再編。外部制約の変化や緊急時も、上書きを既定解にしない。
- **分離・再統合**：引受成立の条件、移行中の責任、権限・資源・資産の引継ぎ。
- **複数Cellにまたがる変更**：版の互換性、受入と適用の順序、部分失敗からの復旧。

ProfileスキーマとFederationの状態遷移・メッセージ形式は、具体例を通して必要なものから定める。
