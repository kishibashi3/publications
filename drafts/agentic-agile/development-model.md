# Agentic Agile — 考え方と開発の姿

> 位置づけ：導入解説（非規範）
> 対象：AAの背景、実行・検証・学習の循環と具体例。
> 参照：[Principles](principles.md)が定義元。仕事の流れや道具は適用例であり、新たな義務を追加しない。

## 1. なぜ開発を組み直すのか

Agentic Agile（AA）は、AIエージェントが主要な実行主体となることを前提に、人間の判断・権限・検証・学習の置き方を組み直す開発原則である。
目指すのは、常時活動するエージェントの集団に人間の判断を接続し、開発を進めながら、その開発系自身も改善する姿である。

出発点は、実装能力の希少性が下がったことにある。
実行は安く速くなるが、実行総量は有限である。人間の判断は希少であり、Agentの出力にはばらつきと共有された誤りがある。
人間が作業を細かく分け、一つずつ指示・確認する構造のまま実行だけを速くすると、人間の判断待ちが残り、誤った方向の実行も速くなる。

そこで、人間の判断を、最も価値のある判断に使い切る。
同じ判断が繰り返されるなら、その条件を規則と環境に移し、次から自律的に進められるようにする。
人間の成果には、自分が判断しなくても適切に動く系を作ることも含まれる。

## 2. 人間とAgentはどう仕事をするのか

人間は目的、守る条件、使える権限、成果の判定条件を整える。
Agentはその範囲で仮説を立て、必要な作業へ分解し、設計・実装・検証・再計画を進める。
未定義の意味や権限外の判断に出会ったら、正当な判断者へ戻す。責任は人間に残る。

| 人間が整えるもの | Agentが実行時に使うもの |
| --- | --- |
| 何を達成したいか | Goalと、その背景 |
| 何を守るか | Rule・Constraint |
| どこまで任せるか | Authority・情報の参照と送信の範囲 |
| 何をもって成果とするか | Acceptance condition・必要なEvidence |

「前の会議で言った」「普通はこうする」は、そのままでは権威の根拠にならない。
目的・意味・権限を明示し、Agentが推測で補う範囲を減らす。
必要な背景や観測情報は共有するが、情報を知ったことによって権限まで増えるわけではない。

設計・実装・テストを恒久的な担当者間の引継ぎにする必要はない。
一つの自律系が、仮説・設計・実装・検証・観測・改訂のループを短く回せる。
人間がすべてのTaskを事前に分解せず、実行系が必要に応じて作業を組み替える。

IssueやTask Backlogはこのループを実装する道具である。Jiraを使うことも、使わないこともできる。
見るべきなのはTask消化数だけでなく、目的、守る条件、委任範囲、成果を支えるEvidenceである。

## 3. 小さく間違え、早く気づく

高速な実行では、誤りの発生確率だけでなく、気づくまでにどれだけ進むかが重要になる。
Principlesは、その判断尺度を期待浪費として置く。

$$
\text{Expected Waste} = P(\text{wrong}) \times W
$$

ここでWは、誤った状態のまま進む実行量である。
同じ単位で数えるなら、誤り確率10%で1単位進む場合は0.1、1%で10,000単位進む場合は100になる。
これは期待浪費の比較であり、個々の誤りの重大性や不可逆な損害まで同じ尺度にしたものではない。

実行を小さく区切り、早く検証すれば、誤りが後続の大量作業へ広がる前に止められる。
同時に、小さな変更、切り戻し、隔離した検証環境、shadow runなどで可逆性を設計する。
戻せる範囲を広げることは、既存の制約を守りながらAgentへ任せられる範囲を広げることにつながる。

ただし、小さな変更の累積が不可逆なら、判断する対象はその累積である。
可逆な変更に分割しただけで権限が増えるわけではなく、戻せない操作は自律範囲から切り分け、人間の判断を求める。

検証にも設計が要る。同じ生成元は同じ盲点を共有するため、判定は異なる主体またはモデル系列で行う。
作る仕事を統合しても、判定の独立性は残す。別のAgent名を付けるだけで誤りの独立性が保証されるわけではない。

品質は一度の成功だけでは決まらない。入力や実行条件による成功・失敗の分布として観測する。
検証の間隔や強さは、リスク、可逆性、期待浪費、影響範囲に応じて設計する。

## 4. 実行するほど開発系が育つ

開発を続けると、曖昧な条件、繰り返す問い合わせ、検証の不足が見つかる。
それを毎回人間が処理するだけでは、同じ判断待ちが続く。
観測とEvidenceを規範・環境の改善へ戻し、次の実行条件を変える。

ここで「憲法の連鎖」が必要になる。
各層は自分に適用される規範のもとで実行し、その範囲内で下位の規則を書く。
例えば、共通の開発原則から案件規則を作り、案件規則のもとで個別作業の条件を具体化する。
原則自身も観測に基づく改訂の対象となる。

Agentは規則の改善案を作れる。自分を縛る条件を緩和する案も、理由とEvidenceを添えて提起できる。
その案を自ら承認し、効力を与えることはできない。
検証の無効化や自己権限の拡大は、切り戻せる変更であっても、この境界を越えない。

改訂の承認と版の扱いは[自己改訂規範アーキテクチャ](../self-revising-norm-architecture/self-revising-norm-architecture-minimal.md)に従う。
通常の実行、規範の改訂提案、改訂の承認を分けることで、自律実行と自己改善を両立させる。

## 5. 一つの変更が成果になるまで

例として、「管理画面の検索に日付範囲を指定できるようにする」変更を考える。
以下は仕事の流れを示す例であり、実証結果や必須工程ではない。

| 場面 | 進め方 |
| --- | --- |
| 条件を整える | 人間が利用目的を共有し、既存の閲覧権限を維持すること、開発環境での変更を許すこと、本番反映は別判断とすることを明示する。境界日付と権限条件を含む受入条件を定める |
| 調べて実装する | Agentが既存仕様を読み、作業を分解して実装する。日付の基準時刻が未定義なら、推測で固定せず照会し、決定を記録する |
| 小さく検証する | 実装を生成した主体から分離した判定者が、受入条件をもとに結果を確認する。異常があれば後続作業を止め、修正・再検証する |
| 成果を確かめる | 差分、検証結果、未解決事項をEvidenceとして残す。本番反映は権限者が判断する。目的が本番での利用なら、開発環境でテストが通っただけでは達成にならない |
| 次へ戻す | 同じ時刻解釈の問い合わせが繰り返されるなら、Agentが案件規則と検証条件の改善を提案する。所有者の承認を経て次の版に反映する |

人間が各Taskへ逐次指示する代わりに、仕事が進む条件と判断すべき境界を明らかにする。
その条件のもとで実行と検証が回り、得られた知見が次の条件を育てる。これがAAの目指す開発の姿である。
