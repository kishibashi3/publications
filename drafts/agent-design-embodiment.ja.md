# 第X章：エージェントの身体性 ― 物理世界に接続するエージェントの設計

## ― 物理世界に接続した瞬間、エージェントは「身体」を持つ

第7章までで、エージェントの安定性は **文脈・実行・時間** の3軸で支えられることを整理した。

しかしこの3軸は、エージェントが概念処理だけで完結する世界を前提にしている。物理世界に接続するエージェント、たとえばカメラ・マイク・物理アクチュエータを持つエージェントを設計しようとした瞬間、3軸だけでは説明しにくい論点が現れる。

- カメラが LAN 内 IP でしか動かない
- マイクと映像と画面表示が同じ「いま」を指していなければならない
- 「コンロの位置」は文脈ではなく、エージェント自身の状態
- Cloud 上のエージェントを、物理アクチュエータに触らせていいのか

これらは「ペルソナの混濁」でも「タスクの混在」でも「時間の混在」でもない。**エージェントの「身体」がどこまでで、その境界をどう守るか** という、独立した論点ではなく **3軸を物理層に投影したときに浮かび上がる新しい設計対象** である。

本章ではこれを **身体性（embodiment）** と呼ぶ。身体性とは、3軸が物理層に投影されたときに現れる新しい設計対象である。

| 元の軸 | 物理層への投影 | 本章の対応節 |
|---|---|---|
| 文脈 | 身体状態（空間記憶、現在位置） | X.3 |
| 実行 | 物理アクチュエータの動作範囲・動作時間 | X.5 / X.6 |
| 時間 | センサーフレームの時間幅、同期窓 | X.6 |

身体性とは、これら 3 つの投影が**同時に矛盾なく機能する設計対象**であり、**物理世界に接続したエージェントが守るべき境界の集合** である。

---

## X.1 身体性の対象 ― 何を「身体」と呼ぶか

「身体」と聞くと比喩に聞こえるかもしれないが、本章で扱う身体は明確に定義できる。

エージェントの身体とは、

- 観察できる物理範囲（センサー）
- 干渉できる物理範囲（アクチュエータ）
- 到達できるネットワーク範囲
- 認識できる時間幅（センサー遅延、アクチュエータ動作時間）

の集合である。これらは設計時に**具体的に列挙できる**。たとえば cooking-agent なら、

- センサー: Tapo C200 のカメラ画角、ホームの音声マイク
- アクチュエータ: PTZ 制御、画面、スピーカー
- ネットワーク: 自宅 LAN
- 時間幅: PTZ 移動 ±3秒、音声往復 ±300ms

このように **具体的な物理範囲の列挙** こそが身体性の出発点である。曖昧な比喩ではない。

> **身体は列挙可能。列挙できなければ守れない。**

---

## X.2 身体は4つの境界の階層を持つ

身体は単一の境界ではなく、**外側から内側へ縮約する4つの境界の階層** で構成される。

```
ネットワーク境界（最も外側 ― どこに到達できるか）
  └ アクチュエータ境界（干渉できる物理範囲）
      └ センサー境界（観察できる物理範囲）
          └ 時間境界（最も内側 ― いつの「いま」か）
```

外側の境界が広くても、内側の境界が狭ければ、**結果として身体の有効範囲は内側で決まる**。たとえば、

- ネットワーク境界が Cloud まで届いていても、
- アクチュエータ境界が LAN 内に閉じていれば、
- そのエージェントは Cloud から物理介入できない。

最も狭い境界が **最終的な Scope** になる。これは設計時に意識すべき重要な性質で、外側だけ見ていると過剰な期待を持ってしまう。

### 1️⃣ ネットワーク境界（reachability）

- LAN 内 / Cloud / Hybrid
- 認証通過範囲
- 物理ルーティング

ネットワーク境界はインフラで強制される。ファイアウォールとルーターが守る境界であり、設計書には書けるがそれだけでは守られない。

### 2️⃣ アクチュエータ境界（action）

- どの物理装置を動かせるか
- どのファイルを書けるか
- どの API を叩けるか

アクチュエータ境界は **副作用の到達範囲**。エージェントの「責任の地理的範囲」と読み替えてもよい。

### 3️⃣ センサー境界（perception）

- カメラ画角
- マイク集音範囲
- データソースの所属

センサー境界の外は、エージェントにとって**存在しない**。どんなに賢くても見えない場所は判断できない。

### 4️⃣ 時間境界（temporal）

- センサーフレーム遅延
- アクチュエータ動作時間
- ユーザーの認知許容時間

身体は「いま」を瞬間ではなく**ある幅を持った時間窓**として持つ。物理動作には時間がかかる。これを無視するとエージェントは未来や過去の情報で判断する。

## X.3 身体状態は文脈ではない

ここが最も誤解されやすい。

エージェントが「コンロは pan=90, tilt=20 にある」と把握しているとき、これは:

- ❌ **文脈** ではない（会話の話題に依存しない）
- ❌ **タスク手順** ではない（実行ステップではない）
- ✅ **身体状態** である（身体の現状記述）

これを文脈に積むとどうなるか。

会話が長くなるにつれて、身体状態が他の発話に汚染される。「コンロを見て」が次第にズレる。料理が30分続けば、エージェントは自分の身体の場所を忘れる。

これは第6章「レポート化アーキテクチャ」の **LLM は分子レポートを読むだけ** という原則の延長である。**身体状態は session state に外置きし、LLM は読むだけ** という設計に落とす。

> **身体状態を文脈に混ぜた瞬間、エージェントは身体を失う。**

---

## X.4 身体の粒度は伸縮する

身体性を持つエージェントの設計では、身体の境界を**固定しない**ことが重要になる。状況によって身体は伸縮する。

たとえば cooking-agent では、

- ユーザーが家にいるとき: 身体は LAN 内、PTZ 操作を含む
- ユーザーが外出中: 身体は Cloud 側に縮約、PTZ は無効、音声・テキストのみ

つまり同じエージェントでも、**動作環境によって身体の粒度が変わる**。

設計原則:

- **身体は静的ではない**。動作環境ごとに身体境界を再計算する仕組みを持つ
- **粒度の伸縮は明示的に**。暗黙に変わると Scope 違反を起こす（外出中なのに PTZ を試行するなど）
- **縮んだ身体は能力を失うことを受け入れる**。Cloud 側ではユーザーに「いまは PTZ が使えない」と明示する

身体の粒度を固定すると、エージェントは「常に LAN 内」「常に Cloud」のいずれかに張り付き、もう一方の状況で破綻する。

---

## X.5 Scope の物理化 ― ネットワーク境界・物理境界・法的境界

第4章で扱った Scope は、概念的な「守備範囲」だった。身体性を持つエージェントでは、Scope は3つの物理層に拡張される。

### ネットワーク境界

- 身体がどのネットワークに属するか
- どこまでアクチュエータが届くか
- LAN-only か Cloud か Hybrid か

「PTZ 操作は LAN 内 IP のみ」のような制約は、Scope を物理ネットワーク層で強制する。設計書ではなくルーターが守る。

### 物理境界

- 身体がいる物理空間
- 触れる物理対象
- 動作する時間帯

キッチンに設置されたカメラは、その家のキッチン以外のものを観察できない。物理境界は工事で決まる。

### 法的境界

- 身体の動作が法的にどこまで許されるか
- どの権限で、誰の代理として動くか
- 監査可能性の範囲

エージェントが家族の所有物に触れる場合と、第三者の所有物に触れる場合で、同じアクチュエータでも法的境界は異なる。

> **Scope は概念だけで守れない。**
> **身体性を持つエージェントの Scope は、ネットワーク・物理・法のいずれかで強制される必要がある。**

## X.6 マルチモダリティ同期 ― 身体の「いま」を一つにする

身体性を持つエージェントは、複数のセンサーモダリティを同時に扱う。

- 音声入力（マイク）
- 視覚入力（カメラ）
- テキスト入力（画面）
- 音声出力（スピーカー）
- 視覚出力（画面）
- 物理出力（PTZ 移動など）

これらが**同じ「いま」を指していない**と、身体は分裂する。

ユーザーが「これ見て」と言いながらコンロを指差したとき:

- 音声: 「これ」（時刻 T）
- 視覚: 指差し方向（時刻 T+0.5）
- 文脈: 直前の発話（料理開始から3分）

これらが同じイベントを指していると認識されなければ、エージェントは「これ」が何か理解できない。

**マルチモダリティ同期は、身体の binding problem である。**

設計原則:

- すべてのセンサー入力に **タイムスタンプを必ず付ける**
- 「同時刻」の判定窓を明示する（例: ±200ms）
- 同期に失敗したらフォールバックを構造化する（例: 視覚未到達なら音声だけで応答）

## X.7 身体性の失敗モード

身体性を意識しない設計が陥る典型を整理する。

### ① 身体感覚なしの自律行動

「Cloud にあるエージェントが、LAN 内のアクチュエータを直接叩く」設計は、身体の延長を誤解している。Cloud のエージェントの身体はネットワーク境界が広い代わりに、アクチュエータ境界が物理装置まで届かない。

```
悪い例:
  Cloud 上の context_agent が PTZ ツール（capture, move_to_and_capture）を直接 tools に持つ

良い例:
  Cloud 上の context_agent は ask_local_body ツールだけ持つ
  PTZ ツールは LAN 内の local_body_agent だけが持つ
  ローカル切断時は ask_local_body が失敗を返し、
  context_agent は「いまは身体が使えません」と応答する
```

→ **物理世界への介入は、必ず LAN 内のローカル身体エージェント経由で行う**。Cloud から直接物理介入させない。

### ② 身体状態の文脈混入

空間記憶を会話履歴に積むと、時間が経つにつれて身体感覚が失われる。

```
悪い例:
  context_agent の instruction に
  「camera は毎回記憶がリセットされる。空間記憶はあなたが持つ」と書く
  → 空間記憶が LLM の会話履歴に積まれ、長時間で漂流する

良い例:
  context_agent の instruction に
  「空間記憶は state['kitchen_map'] に格納されている。判断はこれを読んで行う。
   camera から報告を受けたら update_kitchen_map ツールで書き戻す」と書き、
   update_kitchen_map ツールを実装する
  → LLM は state を読むだけになり、記憶力に依存しない
```

→ **身体状態は session state に外置き**。LLM は読むだけ。

### ③ センサーフレームの過剰信頼

カメラ画像をそのまま LLM の context に渡し続けると、context window が爆発する。

```
悪い例:
  context_agent が capture_image ツールを直接持ち、画像が context window に蓄積する

良い例:
  camera_agent を AgentTool でラップする
  画像は camera_agent のセッション内で消費され、
  context_agent には「名前 | 位置 | 説明」のテキスト報告だけが届く
```

→ **画像は身体の一時状態**。AgentTool で消費し、テキスト報告のみ上位に伝える（第6章レポート化の応用）。

### ④ 同期失敗の暴走

マルチモダリティが同期しないとき、エージェントが「全部最新」と仮定して応答すると、一貫性のない発話になる。

```
悪い例:
  音声・視覚・テキストが独立に到着、エージェントは「すべて最新」と仮定して応答

良い例:
  すべてのセンサー入力にタイムスタンプを付け、±200ms 以内を「同時刻」とみなす
  同期失敗時は Rules で固定したフォールバック発話を返す
  （例: 「映像が遅れています、もう一度言ってもらえますか?」）
```

→ **同期失敗を構造的に検出**し、フォールバック発話を Rules で固定する。

### ⑤ 身体粒度の固定

LAN 内動作を前提にしたエージェントを Cloud に持ち込んだ瞬間、PTZ 呼び出しがすべて失敗する。

```
悪い例:
  エージェントの instruction に「PTZ で見て」と書き、Cloud 環境でも LAN 環境でも同じ instruction を使う

良い例:
  session 開始時に context["body"] を注入する
    context["body"] = {
      "network": "lan" | "cloud",
      "actuators": ["ptz", "speaker", "screen"] or ["speaker", "screen"],
      "sensors": ["camera", "mic"] or ["mic"],
    }
  instruction に「context['body']['actuators'] に "ptz" があれば PTZ を使う、
   無ければ『いまは PTZ が使えません』と応答する」と書く
```

→ **動作環境ごとに身体境界を再計算する**。エージェントが「いま自分はどの身体を持っているか」を判断できる構造を入れる。

## X.8 身体性のチェックリスト

エージェントを設計したら、以下を確認する。

- ✓ 身体の4境界（ネットワーク・アクチュエータ・センサー・時間）が**列挙されている**か？
- ✓ 最も狭い境界が **最終 Scope** として明示されているか？
- ✓ 身体状態と文脈が**分離されている**か？
- ✓ Scope はネットワーク or 物理 or 法のいずれかで**強制されている**か？
- ✓ マルチモダリティの**同期窓**が定義されているか？
- ✓ 動作環境ごとに**身体粒度が再計算される**仕組みがあるか？
- ✓ Cloud 上のエージェントが**直接物理世界に介入していない**か？
- ✓ 身体センサーの返り値（画像・音声）が **context window に常駐していない**か？

**1つでも「No」なら、身体性が壊れている。**

---

## X.9 身体性の設計とは何か

身体を持たないエージェントは、概念処理しかできない。要約、分類、抽象 ― それは強力だが、世界に対して何も**動かせない**。

身体を持つエージェントは、世界に対して責任を持つ。動かせるからこそ、間違えたら被害が出る。だから境界の設計が必要になる。

身体性の設計とは、**「どこまでが自分か」を決める作業** である。広すぎれば暴走するし、狭すぎれば役立たずになる。設計者の仕事は、ユーザーが必要とする身体の粒度を見極め、それに合わせて境界を引くことだ。

## この章のまとめ

- **身体性は3軸（文脈・実行・時間）を物理層に投影したときに現れる設計対象**
- **身体は4つの境界の階層**を持つ: ネットワーク → アクチュエータ → センサー → 時間
- **最も狭い境界が最終 Scope** を決める
- **身体状態は文脈ではない**: session state に外置きし、LLM は読むだけ
- **身体の粒度は固定しない**: 動作環境ごとに再計算する
- **Scope はネットワーク or 物理 or 法で強制**する
- **マルチモダリティ同期は身体の binding problem**
- **身体性の設計とは、エージェントの「どこまでが自分か」を決める作業である**
