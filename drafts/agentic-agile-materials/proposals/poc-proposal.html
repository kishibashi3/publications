01 / Executive Summary

PoCで答えるべき問い

「全チームをFull Agenticにすべきか？」ではなく、
「どこまでAgent化すれば十分なのか？」を明らかにします。

本番前に知りたいこと

  • Agentic開発は基幹領域で本当に成立するか
  • 従来型チームは周囲の速度についていけるか
  • Full AgenticとHalf Agenticの差はどこに出るか
  • どのDomainに高いAgent Literacyが必要か
  • EAA Coreで異種Delivery Modelを接続し、必要なProfileだけを追加できるか
  • 品質・統制・説明責任を保てるか

PoC終了時に返すもの

  • Domain別 推奨Delivery Model
  • Domain別 必要Agent Literacy
  • 生産性・品質・人間負荷の実測値
  • Cross-domain bottleneck map
  • 10億円本番向け EAA Core / Active Profiles / Local Delivery構成
  • 組織・教育・統制案
「Full Agenticが最も速い」という結論を前提にしません。差が小さいなら、それ自体が本番での過剰投資を防ぐ重要な成果です。
02 / What is EAA

EAAはAI駆動開発をEnterprise規模で成立させる開発・統治モデル

内部の作り方を統一しない。
意味・Mission・権限・境界・Evidenceだけを企業として共有する。

EAA Instance = Core + Active Profiles + Local Delivery Models + Reference Patterns
Core
すべてのEAAに必須の最小規範。
Domain / Mission / Ontology / Authority / Contract / Evidence / Durable Provenance / Escalation / Enterprise Constraints
普遍でない規範をCoreへ入れない
Profiles
案件条件に応じて追加・解除する統制。
Portfolio / Assurance / Supplier / Regulated / Migration / Cutover
必要な統制を必要な場所と時間にだけロード
Local Delivery
Domain内部の実行方式は自治。
Full Agentic / Human + Agent / Scrum / Kanban / SAFe ART / Predictive / Package / Vendor proprietary process
Patterns
交換可能な非規範的実装例。
GitHub Mission Ledger / Mission & Evidence Graph / Daily Evidence / Transparency Report / Capability & Enabling
EAA Compliance ≠ Internal Process Compliance
DomainがMissionを受け取り、Ontology / Contractを解釈し、Authorityを越えず、Required Evidenceを返し、Escalationできれば、 内部がAgenticでもScrumでもPredictiveでもよい。

04 / Experiment Design

3種類のDelivery Teamを同じEnterprise Deliveryに入れる

Team想定Agent Literacy開発モデルPoCで見ること
Full Agentic L3 Mission単位でAgentへ委任。再帰分解、実装、検証、Evidence生成までAgent主体 自律実行の上限、Human Touch Time、品質、Evidence密度
Half Agentic L2 Scrum/Kanban + Agent。Issue単位で設計〜実装を委任 現実的なAI活用でどこまで差を縮められるか
Legacy L1以下 現行に近いScrum/工程型。AI利用は禁止しない 周囲がAgentic化した際の待ち時間・負荷・必要最低Literacy
Legacy Teamを「AI禁止」にしないことが重要です。途中でAgent利用を増やす必要が生じたなら、それ自体を実験結果として扱います。
05 / Agent Literacy

Agent LiteracyをL1〜L3で仮定義し、実験後に修正する

L1
Assisted

人間が仕事を分解し、Agentを道具として使う。

  • 調査
  • コード生成
  • テスト生成
  • 文書化
L2
Delegated

Issue / Outcome単位でAgentへ委任できる。

  • 設計
  • 実装
  • テスト
  • レビュー補助
L3
Agentic

Mission単位で自律系を運営する。

  • 再帰分解
  • 並列Agent
  • 独立検証
  • Evidence生成

目的は全員をL3にすることではなく、
DomainごとのMinimum Sufficient Literacyを見つけること。

06 / Two Types of Work

比較実験とEnterprise統合実験を分ける

A. Comparable Missions

3チームへ同程度の課題を与え、Delivery Modelそのものの差を比較する。

  • API追加
  • DB schema変更
  • 業務ルール変更
  • 障害修正
  • Legacy調査

B. Enterprise Vertical Mission

3チームが異なるDomainを担当し、一つの業務OutcomeをEnd-to-Endで完成させる。

Partner→ Full→ Half→ Legacy→ Evidence
これにより「Domainが難しかったから遅い」のか、「Delivery Modelの差で遅い」のかを分離して観察できます。

11 / Truthfulness by Design

「嘘をつけない」ではなく、「曖昧にしにくい」管理へ

従来の月次報告

設計 100% / 製造 85% / テスト 42% / 総合進捗 71%

何が完成し、何が壊れ、なぜ遅れたかは分かりにくい。

EAA Transparency

  • どのMissionが完了したか
  • 何がBlockedか
  • どこで手戻りしたか
  • どの意思決定が原因か
  • 何をEvidenceとして完了したか

Reworkの原因も両方向に見える

Rework ¥6.8M ├─ Customer requirement change ¥2.6M ├─ Vendor design error ¥1.7M ├─ Legacy behavior discovery ¥1.4M ├─ Cross-domain misunderstanding ¥0.8M └─ Experiment / learning ¥0.3M
発注者・受注者のどちらか一方を監視する仕組みではなく、プロジェクト全体の因果を透明化する仕組みです。
12 / Literacy Intervention

Full Agentic Teamが早く終わったら、教育投資の効果まで測る

Baseline→ 差を観測→ L1→L2 / L2→L3 教育→ 再測定

教育前

  • Lead Time
  • Human Touch Time
  • Boundary Wait
  • Evidence Coverage

教育後

同程度のMissionを再度流し、教育によって性能差が縮むかを確認。

Education ROI = Saved Delivery Cost / Training Cost

これにより、本番で「全員にL3教育」ではなく、「このDomainには最低L2」という投資判断が可能になります。
