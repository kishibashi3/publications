# EAA解説 — AAから分割とFederationへ

> Status: explanatory draft / non-normative
>
> [Core](enterprise-agentic-agile-core-v0.1.md)の理由と使い方を説明する。
> 旧「構成原理」と「AAからの拡張」を統合した。定義はCoreと[Profiles](eaa-profiles-v0.1.md)を参照する。

## 1. AAから始める

AAは人間の判断とAgentの実行・検証・学習を成立させる、単独で使える開発原則である。
親Cellや別チームの存在を必要としない。EAAはその開発主体を一つのCellとして扱う。

一つのAAで全責務を担う間は、そのまま開発を進められる。
拡張が必要になったら、現在担う責務と新たに必要な責務をProfileとして記述し、引受先を決める。
Profileは分割可能な責務を明らかにするための仕様であり、AAの開始条件ではない。

## 2. 組織図より先に責務を置く

必要な専門能力が増えるたびに専用組織を作ると、調整先も増える。
まず責務を定義すれば、同じCellで担うことと、独立したCellへ移すことを選べる。

Standard ProfileはPlatformなど再利用可能な責務、Domain Profileは契約・請求など業務固有の責務を表す。
同じ形式を使い、Profileの数だけCellを置く必要はない。

Enterprise／Domainは全体と部分という位置の呼び名であり、Platformなどは担当責務の名前である。
同じCellが全体として子Cellを持ち、より大きな全体の一部にもなれる。

## 3. 分割しても開発原則は変わらない

| 構成 | EAAから見た姿 |
| --- | --- |
| 一つのAAが全責務を担う | 1 CellのEAA |
| 分割後の各主体がAAで動く | AAを内部方式に持つ複数Cell |
| 一つのCellがさらに分割する | 外部には一つの責任主体、内部には複数Cell |
| AAと既存チームが協働する | 内部方式の異なるCellのFederation |

責務の引受範囲が変わっても、AAの原則そのものを書き直す必要はない。
AAの規範の層と、Cellの親子関係は別の構造である。内部TaskをAgentへ配るだけでは独立Cellへの分割にはならない。

Federationは、責任・権限・合意・Evidenceを通して相手と接続する。
相手がAgentを使うか、どの工程で実装するかを接続条件にしない。1 Cellであることだけで、非Agenticな主体までAAになるわけではない。

## 4. 自治を変更手続きで支える

「自律してよい」と宣言しても、親が後から条件を直接書き換えられるなら、判断権限は安定しない。
そこで、変更の提案と対象Cellの受入を分ける。DomainからEnterpriseへのOntology訂正も、PlatformからDomainへのCI/CD導入も同じ関係である。

共通規範の正本を一つにしても、各Cellが採用する版を固定すれば、一方的な変更の波及を防げる。
正本を改訂する権限と、それを採用する判断は別になる。具体的なライフサイクルはProfiles、PRでの実装例は[適用ガイド](eaa-delivery-guide-v0.2.md)を参照する。

自治には、既に引き受けた保証を果たす責任も伴う。
変更を受け入れない場合に既存義務まで消えるわけではなく、履行不能は調整の対象となる。

## 5. IaC化からPlatformを分離する例

これは構成例であり、効果の実証ではない。役割の配置は[Role Model](eaa-role-model-v0.1.md)の例を使う。

1. 一つの開発主体で業務機能と基盤を扱う。
2. Enablerが顧客との会話・問題・残件をIssueへ戻し、OpeとAgentが土台・計画・実装・検証を進める。
3. 基盤の継続的な判断負荷が増えたら、Platform責務をProfileとして明らかにし、別Opeへの引受を合意する。
4. 権限・資源・資産・記録・残件を移し、Platform Cellを独立させる。
5. 以後、CI/CDの変更や基盤改善は、相互の提案と受入で進める。

分離で変わるのは責務を担う主体と接続方法である。
親Opeへの判断集中が減り、成果と外部保証を維持できたかで、分離の効果を確認する。
